## 用語メモ（初出のみ）

- **採点方式（スコアラー）**：会話の各項目に「今の仕事にどれだけ必要か」の点数を付ける方法。ctxjev には次の4つがあります。
  - **Jev**：TypeSafe AI 社の高速・安価な判定専用 AI。外部 API に送って判定してもらう。
  - **単純な切り捨て（recency）**：新しい項目ほど高い点数。内容は見ない。現在の既定。
  - **キーワード一致（local）**：目標文と同じ単語がどれだけ含まれるか。オフライン。
  - **ランダム順（random）**：乱数で並べた比較用の基準。これに勝てなければ「選んでいる」とは言えない。
- **予算**：剪定（不要な履歴を削ること）後に残してよいトークン数の割合。25% なら元の4分の1まで削る。
- **dev（開発用データ）**：設計や調整に使ったデータ。ここでの数値は楽観的になりやすい。
- **ホールドアウト**：設計に使わず、最終判定のためだけに取っておくデータ。
- **事前登録**：結果を見る前に「何をどう測り、どう判断するか」を文書で固定すること。後から都合よく基準を変えられなくなる。
- **95%CI（信頼区間）**：データのぶれを考慮すると、本当の差がおそらくこの範囲にある、という幅。下限が 0 より上なら「差がある」と言いやすい。
- **切り取り点**：記録した会話のうち「では修正して」と依頼した直前の位置。評価ではここまでの履歴を剪定してエージェントに渡す。

### 1.4 分かっていること・分かっていないこと

**分かっていること（証拠あり）**

- 剪定の安全性：ツール呼び出しと結果の対を壊さない、先頭と末尾を保護する、会話を大きくしない（ラウンド1で修正・検証）。ランダムな入力による性質テストで確認済み。
- 秘密情報のマスキング：監査の40形式（再構成）すべてを隠し、無害な22例を変えない（ラウンド1）。ただし「ベストエフォート」（見つけられる形式だけ）であることは変わりません。
- 強いエージェント（Sonnet 5）と 25% 予算の小さな課題では、どの剪定方式でもほぼ全課題を完了できる。

**分かっていないこと（証拠なし、または否定的）**

- **Jev の順位付けが、単純な方法（切り捨て、キーワード一致、ランダム順）より課題の成果を良くすること。** 設計に使った dev では良く見えましたが、ホールドアウトでは示せていません。副指標ではランダム順以下でした。
- プラグインが実際の Claude Code の圧縮後に役立つこと（dev の模擬圧縮で差はノイズの範囲、ホールドアウトの模擬圧縮では2回とも効果を示せず、本物の圧縮では未測定）。
- 課題が作者自身の作った同じ型のものに限られるため、他の種類の作業にどこまで一般化できるか。
- AI による採点（質問応答の正誤判定）が人間の判断とどれだけ一致するか。

### 1.5 今のホールドアウトはもう「確認」に使えない

今回の6課題は、結果を見て、失敗の理由を分析し、指標の問題点まで調べました。この先ここで何を測っても、それは「見た後の分析」であり、新しい主張を確認する証拠にはなりません。ラウンド2で効果を主張するには、**新しい課題を作り、結果を見る前に事前登録する**必要があります（第3節）。

## 2. 選択肢

### 選択肢 A：安全で決定論的な剪定器として位置づけ直す

**何を変えるか**
- 製品の説明を「賢く選ぶ」から「安全に削る」へ変える。既定は切り捨て（recency）＋構造的な保護（ツールの対を壊さない、利用者の発言を残す、削除箇所の注記、先頭と末尾の保護、会話を大きくしない、プロンプトキャッシュへの影響の報告）。
- 「決定論的」（同じ入力なら必ず同じ出力）な保護を追加：エラー出力・失敗したテスト結果は残す、同じファイルの古い読み込みは新しい読み込みがあれば削る、など。
- Jev は任意機能として残すか外す（外す場合は選択肢 D）。
- 成功の測り方を変える：順位付けの良さではなく、①安全性の不変条件が常に守られること、②トークンとキャッシュ費用の節約量、③全履歴を渡した場合と比べて課題成功率が**劣らない**こと（非劣性：差の区間の下限が、あらかじめ決めた許容幅、たとえば −10 ポイントより上）。

**費用**：実装は数日（S〜M）。評価は非劣性の確認のみなので中程度（第3節の見積もりの一部）。

**リスク**：「既存のツールと何が違うのか」という価値の訴求が弱くなる。名前（ctx**jev**）と中身がずれる。

**点数が認められるために証明が必要なこと**：新しいホールドアウトで、剪定後の課題成功率が全履歴に対して非劣性であること。節約トークン数とキャッシュ影響の実測値を保存データから示すこと。

### 選択肢 B：複数の安価な手がかりを組み合わせた採点（ハイブリッド）

**何を変えるか**
- 次のような「安くて決定論的な手がかり」を組み合わせて点数を出す新しい採点方式を作る：
  - 目標文や直近の発言との語の類似度（BM25：検索エンジンで使われる標準的な類似度計算）
  - 新しさ（recency）
  - エラー出力・失敗したテストの出力かどうか
  - 後の項目によって置き換えられたか（同じコマンドの再実行、同じファイルの再読み込み、修正後に通ったテスト）
  - ファイルパスや識別子（関数名など）が後の会話で参照されているか
  - 利用者が述べた制約（「〜は変えないで」「24時間」など）を含むか
- Jev は「任意の1特徴」として加えられるようにする（選択肢 C の質問を含む）。
- 閾値（「0.3 未満は削除」のような絶対値）をやめ、**予算内で上位から残す**方式（上位 N 件、またはトークン予算）にする。これで `local` の閾値が合わない問題（監査の #6）も解消します。
- 手がかりの重み付けは **dev データだけ**で決め、ホールドアウトでは一切調整しない。

**採点項目への影響（見込み）**：新しいホールドアウトで実際に切り捨てとランダム順を上回れば、2a ＋2.5〜4.5（最大の伸びしろ）、2b ＋1.5。上回らなければ 2a はほぼ動かず、A と同じ位置づけに戻ることになります。3a は評価のやり直しで＋1.5〜2.0。

**費用**：実装は1〜2週間（M〜L）。評価費用は 3.8 節の見積もりのとおり。

**リスク**：dev への過学習（dev では強いがホールドアウトでは効かない。今回 Jev に起きたこと）。手がかりが多いほど過学習しやすいので、重みの数は少なく保つ必要があります。

### 選択肢 C：Jev に聞く質問を変える

**何を変えるか**

**採点項目への影響**：B と同じく、新しいホールドアウトで効果が出た場合のみ 2a が伸びます（＋1.5〜3.0）。

**費用**：質問の変更自体は小さい（S）。dev での質問文の比較（数セント）と、ホールドアウトでの評価が必要。

**リスク**：Jev は文章生成も計算もできない「判定専用」の AI です（CLAUDE.md の制約）。置き換え検出には、比較対象の後の項目を一緒に見せる必要があり、1回の要求の状態（state）が大きくなります。また、これまでの結果から Jev の判定は実行ごとの揺れが大きく、1回ごとの再採点が必須です。

**費用**：コードの削除は小さい（S）。改名は npm・プラグイン・ドキュメントの移行で M。

**リスク**：プロジェクトの出発点（Jev の活用）を捨てることになる。改名は既存利用者を混乱させる。

### 3.5 AI による採点の人手抜き取り検査

今までのプラグイン評価は、Claude Haiku に要約させる「模擬の圧縮」でした。本物の圧縮の内容は公開されていないため、実物で測ります。

1. 課題ごとに、記録済みセッションの切り取り点までを Claude Code の会話として再現する（`claude -p --resume <session id>` で記録済みの会話を続ける）。
2. 個人設定のない専用の設定ディレクトリ（`CLAUDE_CONFIG_DIR`）で、プラグインを入れた環境と入れない環境を用意する。
3. `/compact` を送って本物の圧縮を起こし（フックが動く）、その後に修正依頼を送る。
4. 隠しテストで成否を判定する。条件はプラグインあり／なし、各3回、12課題。
5. 実行環境のプロキシ設定をフックの子プロセスに渡す（前回はこれがなく Jev に届かなかった）。フックが実際に Jev で採点したかを `last-run.json` で確認し、オフラインに落ちた実行は別に数える。

- **エージェントの隔離**：本物の圧縮の検証でも、エージェントのコマンドと隠しテストは第7節のサンドボックスで実行する。`claude -p` 自体の実行（記録と圧縮）は Claude Code の権限設定に従う点が異なり、2a で実装するときに `--allowedTools` と使い捨ての `CLAUDE_CONFIG_DIR` で範囲を絞る。

### 3.7 判断ルール（案）

- **主判断**：主予算（15%）・Haiku で、「候補の採点方式（B を選べばハイブリッド、そうでなければ Jev）− 切り捨て」の課題成功率の差について、95%CI（課題単位のクラスタ・ブートストラップ：課題ごとにまとめて再標本化し、同じ課題の反復を独立扱いしない方法）の下限が 0 より上、かつ Sonnet での点推定が 0 以上なら、その方式を既定にできる。
- **偶然との比較**：同じ条件で「候補 − ランダム順」の下限も 0 より上であること。これを満たさなければ「選んでいる」とは言わない。
- **副指標**：修正依頼までの保持率で、候補 − 切り捨て、候補 − ランダム順の下限が 0 より上なら「必要な事実をより多く残す」と書いてよい。
- **非劣性（選択肢 A）**：全履歴 − 切り捨て（出荷設定）の差の上限が 10 ポイント未満なら「全履歴に劣らない」と書いてよい。
- **無効の判断**：候補 − 切り捨ての差の上限が 5 ポイント未満なら「意味のある効果はない」と結論し、A（または D）の位置づけにする。
- **Jev を残す条件**：ハイブリッド（Jev あり）− ハイブリッド（Jev なし）の下限が 0 より上。満たさなければ Jev は既定から外す（D を検討）。
- 複数の予算・比較をしているので、主判断は上の1つに限定し、それ以外はすべて「副次的」と明記する。
- 精度の目安：<!-- generated:design-precision -->dev（10課題×2回）での差の95%CI幅は 30 ポイントでした。課題数だけで単純に換算すると 24 課題では約 19 ポイント<!-- /generated:design-precision --> です（実際の幅は課題ごとのばらつきで変わります）。これより小さい効果は検出できない可能性が高いことを、登録時に明記します。

## 4. 推奨と理由

**推奨：A を土台にしつつ B を候補として検証し、C の「置き換え検出」の質問は B の中の任意の特徴として試す。D は新しいホールドアウトの結果で決める。**

理由：

1. **A はすぐに価値があり、失うものがない。** 既定はすでに切り捨てで、ラウンド1で安全性（会話を大きくしない、秘密を隠す、対を壊さない）を固めました。これを製品の中心に据えれば、説明と実態が一致し、2b・3a・7a が確実に伸びます。
2. **B の手がかりは A の安全装置と重なる。** 「エラーや失敗したテストを残す」「置き換えられた古い結果を削る」は、順位付けの手がかりであると同時に安全装置でもあります。作る価値は評価の結果に関係なく残ります。
3. **Jev を今すぐ捨てるだけの証拠はまだない。** 今回の否定的な結果は、天井効果のある主指標と、構造的に歪んだ副指標によるものも大きく、「Jev が役に立たない」ことの証明にもなっていません。Jev を B の1特徴として、あり・なしを直接比べれば、残すべきかどうかをはっきり決められます。
4. **95点に近づく唯一の道が 2a（6点）である。** 2a は「単純な基準より成果を改善する証拠」で、新しい評価で本当の効果が出ない限り上がりません。B と C を正しく設計した評価にかけることが、その可能性を残す唯一の方法です。効果が出なければ、A（と D）の位置づけで誠実に説明し直します。

- 2b-7：`node eval/check-docs.mjs --write` で文書の数値を生成し、事前登録の判断ルールを機械的に当てはめて、結果を README と事前登録文書に書きます。否定的な結果も同じ形で載せます。

## 7. 評価エージェントの隔離（サンドボックス、ラウンド1.5で実装）

評価では、AI エージェントが課題のリポジトリの複製の中で実際にコマンドを実行します。以前はそのコマンドが、この PC の利用者と同じ権限で動いていました（複製の外のファイル、たとえばこのリポジトリの `.env.local` にある API キーも読めた）。ラウンド1.5で、エージェントの Bash コマンドと、エージェントのコードを実行する隠しテストを「サンドボックス」（外から切り離した実行環境）の中で動かすようにしました（`packages/core/eval/sandbox.mjs`）。

**方式**（`CTXJEV_SANDBOX` で指定。既定の `auto` は、使えるもののうち上から順に選ぶ）：

| 方式 | 使える環境 | 中身 |
| --- | --- | --- |
| `docker` | Docker が動く環境（Mac なら Docker Desktop） | コマンドごとにコンテナを起動。ネットワークなし、ルートは読み取り専用、権限をすべて外す、プロセス数・メモリ・CPU の上限、複製だけをマウント。`auto` はイメージが手元にあるときだけ選ぶ（`docker pull node:22-bookworm` を1回） |
| `bwrap` | Linux（bubblewrap が入っている場合） | 名前空間で分離し、システムのディレクトリだけを読み取り専用で見せる |
| `unshare` | Linux（ユーザー名前空間が使える場合） | 同上を `unshare` と `chroot` で行う |
| `sandbox-exec` | Mac（標準搭載） | ネットワークを禁止し、ホームや一時フォルダ、このリポジトリを読めなくし、書き込みを複製だけに限る |
| `none` | どこでも | 隔離なし。`CTXJEV_SANDBOX=none` と明示したときだけ（警告を表示） |

**実行前の検査（失敗したら実行しない）**：エージェントを動かす前に毎回、サンドボックスの中から次を確かめます。複製が読み書きできる、node と git が動く、複製の外のファイル・ホームフォルダに置いた検査用ファイル・このリポジトリ・複製の外への書き込み・ネットワークがすべて使えない。どれか1つでも失敗すると、エージェントは1回も動きません。この環境で試せない方式（`bwrap`、`sandbox-exec`）でも、設定の誤りがあればここで止まります。

**確認済みのこと**：この作業環境（Linux）で `unshare` と `docker`（Docker Hub に接続できないため、この PC のファイルから組み立てたイメージ）の両方で検査に合格し、`tasks.mjs --selftest` が16課題すべてで ok（脱出の試み5種類をすべて拒否）。GitHub の CI でも、`unshare` と実際の `node:22-bookworm` イメージの `docker` の両方で同じ自己検査が合格しています（CI の `eval-harness` ジョブで毎回実行）。隠しテストの結果は、隔離前とまったく同じでした。

**防げること**：
- 複製の外のファイルを読む・書く（ホーム、このリポジトリと `.env.local`、ほかの一時ファイル）。
- ネットワークへの接続（データの持ち出し、外部からのダウンロード）。
- API キーの読み取り（環境変数は最小限だけを渡す）。
- シンボリックリンク（別の場所を指すリンクファイル）経由の脱出：ファイル操作の道具（Read・Edit・Write・Grep・Glob）はサンドボックスの外で動くため、リンクをたどった先が複製の中かを実際のパスで確かめ、その実際のパスだけを操作します。行き先がまだ存在しないリンクは拒否します（そこに書き込むと、リンクが指す複製の外の場所にファイルができてしまうため。独立レビューで見つかり修正し、自己検査の5種類目として毎回確かめています）。書き込みの最後の一歩はリンクをたどらない方法で開きます。
- エージェントが書いたコードの実行による上記すべて（隠しテストもサンドボックスで実行）。

**防げないこと（限界）**：
- `unshare`・`bwrap`・`sandbox-exec` では、メモリと CPU の使いすぎは制限しません（コマンドごとの時間制限 60秒、隠しテストは120秒のみ）。`docker` はメモリ 1GB・CPU 2・プロセス 256 に制限します。
- Linux の名前空間とコンテナはホストの OS の中核（カーネル）を共有するため、カーネルの脆弱性を突かれると防げません。Mac の Docker Desktop は仮想マシンの中で動くので、この点ではより強い分離です。
- 読み取り専用で見せているシステムのファイル（`/usr` など。`/etc` はユーザー名などごく一部だけ）は読めます。秘密情報は置かれていない場所です。
- 課題のリポジトリの中身（履歴を含む）は当然見えます。隠しテストはエージェントの作業が終わってから複製に置くので、作業中には見えません。
- Mac の `sandbox-exec` は Apple が非推奨にしている仕組みで、この環境では試せていません。実行前の検査に失敗した場合は Docker Desktop を使ってください。
- ファイル操作の道具の「確かめる」と「書き込む」は一瞬の差がある別々の操作です。その間にエージェントが裏で動かし続けたプロセスが途中のフォルダをリンクに差し替えると、複製の外に書けてしまう可能性があります。Linux の方式（`docker`・`unshare`・`bwrap`）ではコマンドの終了と同時にそのプロセスもすべて終わるため起こりませんが、Mac の `sandbox-exec` ではプロセスが残れるため、理論上は残ります（最後の一歩だけはリンクをたどりません）。
- セッションの記録（`record.mjs` が動かす `claude -p`）は、このサンドボックスではなく Claude Code 自身の権限設定（最後の依頼まで読み取り専用の道具だけ）で制限しています。

## 8. AI 採点の人手チェック用ページの使い方（Q4、クリック手順）

AI（Claude Sonnet 5）が「モデルの回答は正しいか」を判定した結果を、あなたが1件ずつ確かめるためのページです。ページはあなたの PC の中だけで動き、判定はクリックのたびに自動で保存されます。ラウンド2の本番（120件）では、2b-6 で私（Claude Code）が抽出したファイルを用意し、同じ手順で開きます。以下は、今すぐ試せるお試し版（6件）の手順です。

**最初の1回だけ（準備）**

1. Node.js 22 を入れます。ブラウザで <https://nodejs.org> を開き、「LTS」と書かれたボタン（バージョン 22 以上）をクリックしてダウンロードし、ダウンロードされたファイルをダブルクリックして、画面の指示どおり「続ける」「インストール」をクリックします。
2. 「ターミナル」を開きます。Finder を開き、左の「アプリケーション」→「ユーティリティ」フォルダ →「ターミナル」をダブルクリックします。
3. ターミナルに次の2行を1行ずつ貼り付けて、それぞれ Enter キーを押します（リポジトリをホームフォルダに取得します）。

   ```bash
   git clone https://github.com/x96x64/ctxjev.git
   cd ctxjev
   ```

   2回目以降は `cd ctxjev` だけで構いません（最新にするには続けて `git pull` を実行）。

   初めて `git` を使う Mac では、1行目で「"git"コマンドを実行するにはコマンドライン・デベロッパ・ツールが必要です」という画面が出ます。「インストール」をクリックし、利用許諾の画面で「同意する」をクリックして、終わるまで待ちます（数分〜十数分）。終わったら、1行目をもう一度貼り付けて Enter を押してください。

   手順は Mac 用です。Windows の場合は、「ターミナル」の代わりに「PowerShell」（スタートメニューで「PowerShell」と入力）を使い、<https://git-scm.com> から Git を入れてから同じコマンドを実行します。

**ページを開く（コマンド1つ）**

4. ターミナルに次を貼り付けて Enter を押します。ブラウザが自動で開き、ページが表示されます。

   ```bash
   node packages/core/eval/review.mjs --demo
   ```

   ブラウザが開かないときは、ターミナルに表示された `http://127.0.0.1:…` で始まるアドレス（`#` 以降も含めて全部）をコピーし、ブラウザのアドレス欄に貼り付けて Enter を押します。

**判定する**

5. 画面上部の「使い方」を読みます（判定の基準が書いてあります。AI の採点者と同じ基準です）。
6. 各項目で「質問」「正解の事実（期待される答え）」「モデルの回答」「AIの判定」を読み、あなたの判定として「正しい」「誤り」「判断できない」のどれかをクリックします。押したボタンに色が付き、画面下に「保存しました」と表示されれば保存済みです。
7. 気になった点があれば「メモ（任意）」欄に書きます（自動で保存されます）。
8. 「次へ →」で次の項目へ進みます。「未判定の次の項目へ」を押すと、まだ判定していない項目に飛びます。キーボードでは 1＝正しい、2＝誤り、3＝判断できない、←→で前後に移動できます。
9. **本番（120件）では、「AIの判定を、自分の判定を入れるまで隠す」にチェックを入れてから始めてください**（AI の判定が先に見えると、それに引きずられるおそれがあるため。事前登録でこの設定を決めます）。お試しでは、どちらでも構いません。
10. 途中でやめても大丈夫です。ブラウザのタブを閉じ、ターミナルで Ctrl キーを押しながら C キーを押すと終了します。もう一度 4 のコマンドを実行すると、続きから再開できます。

**書き出す・終える**

11. 全部終わったら「判定をJSONで書き出す（ダウンロード）」をクリックします。「ダウンロード」フォルダに `ai-grader-review-日付.json` が保存されます（念のための控えです。判定そのものは自動で保存済みです）。
12. ターミナルで Ctrl＋C を押して終了します。
13. 本番のときは、Claude Code に「人手チェックが終わった」と伝えてください。保存された判定ファイル（`<項目ファイル名>.review.json`）から一致度（κ）を計算し、コミットします。お試し版の判定は、リポジトリに残らない場所（`demo` フォルダ）に保存されます。
