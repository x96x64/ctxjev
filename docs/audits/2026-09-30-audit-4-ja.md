## 4. カテゴリ別詳細レビュー

### 4.1 核心機能（12.5 / 15）

**このツールの仕組み（用語の説明をかねて）**

- 記録の各項目（ユーザーの発言、AI の返事、道具の実行結果）に点数を付け、閾値（区切りの値）で「残す／要約の候補／削る」に分けます。既定では 0.3 未満を削り、0.6 未満を要約の候補にします。
- **トークン**は、AI が文章を数える単位です。予算（`--target-tokens`）を指定すると、その量に収まるまで点数の低い項目から削ります。

**良い点**

- **守るべき約束が崩れない。**
  - 公開されている入口（関数・CLI・MCP のツール）に、壊れた値や極端な値を機械的に総当たりで入れるスクリプト（`scripts/boundary-bruteforce.mjs`）を実行しました。1,958 件で違反は 0 件でした（検証 12）。
  - リポジトリのサンプル 8 件すべてに、`recency` と `local` の2通りで `analyze`（判定の表示）と `prune`（実際に削る）をかけました。ツールの呼び出しと結果の対、最初のメッセージ、最新のやり取り、「削っても大きくならない」、削った場所の注記は、すべて守られました（検証 10）。
  - 予算超過の印（`overBudget`）が正しいかを、目標の量を 824 通り変えて調べました。「印が無いのに超えている」は 0 件でした（検証 C3）。前回の監査の指摘（807 通り中 38 件で誤り）は直っています。
- **説明書と出力が一致する。** README のコンソールの出力例（`README.md:145-157`、`:416-425`）は、実際の出力と1バイトも違いませんでした（検証 7）。
- **独自形式の `prune` が最初の依頼を守る。** ユーザーの項目がある3つのサンプルで「1 protected as the first user entry」と表示され、元のファイルの他の項目（`groundTruth` など）も出力に残りました（検証 C2）。

**問題点と根拠**

1. **MCP の2つのツールは Jev に固定されている。** `packages/mcp-server/src/tools.ts:51` と `:69` で `scorer: 'jev'` が書き込まれています。キーが無いと、呼ぶたびにエラーになります（検証 18）。CLI やプラグインは既定でオフラインなのに、MCP だけはオフラインで使えません。
2. **`.mcp.json` がビルド前には存在しないファイルを指す。** `packages/mcp-server/dist/index.js` はビルドしないとできません。この監査のセッション自体でも、開始時に ctxjev の MCP サーバーが「CONNECTION_CLOSED」で接続に失敗しました。MCP の README には「ビルドが必要」と書いてあります。
3. **既知の小さな不具合（issue #20）。**
   - ユーザーの項目が無く、ツールの結果から始まる記録（`checkout-bug.json`、`memory-leak.json`）では、先頭の2件が警告なしに消えます（`packages/core/src/pruneEntries.ts:48` が「最初のユーザーの項目」だけを守るため）。
   - `--protect-last ""`（空の値）は、エラーにならず 0（保護なし）として扱われ、終了コード 0 で終わりました（今回再現）。
4. **BOM 付きの JSON を受け付けない。** 先頭に BOM（Windows のメモ帳などが付ける3バイトの目印）がある JSON を `analyze` にかけると、「✖ could not parse this file: it's not valid JSON (Unexpected token '﻿' …)」で終了コード 1 になりました（検証 11）。`packages/cli/src/transcript.ts` が BOM を取り除いていません。
5. **Jev の経路は未検証。** ライブテストと評価ゲートは、キーが無いので動かしていません（第9節）。

**減点理由**

- 1a（−1）：問題点3。
- 1b（−1）：問題点1・2・5。
- 1c（−0.5）：問題点4。

### P0-1 引用符なしの `.env` 値に記号が入ると秘密が漏れる

- **優先度**：P0
- **問題**：`DB_PASSWORD=Qx7vR2mK(pL9zW4tB` のように、引用符なしの値に `& ( ) , ; < > [ ] { }` のどれかが入ると、値の全部または後半がマスクされずに外部（Jev）や保存ファイルに出ます。パスワード生成ツールはこうした記号をよく使います。
- **根拠**：`packages/core/src/redact.ts:321-322`（引用符なしの値に使ってよい文字の決まり＝文字クラスが、これらの記号で止まる）、`redact.ts:395`（値の直後が `(` か `[` なら「コード」とみなしてマスクしない）。自作の検査（6種の名前×3種の区切り×28記号）で、11記号がそれぞれ 18/18 件漏れ。`(` と `[` は値全体が、他は記号より後ろが残ります。引用符付きなら正しくマスクされます。
- **改善案**：行頭の `NAME=value`（`.env`・`export`）に限り、値を行末までとみなす規則を先に適用する。

  ```ts
  // .env / shell: `NAME=value` at the start of a line — the value runs to the end of the line.
  const ENV_LINE = /^([ \t]*(?:export[ \t]+)?)([A-Za-z_][A-Za-z0-9_]{0,127})([ \t]*=[ \t]*)(?!["'`])(\S[^\n]*?)[ \t]*$/gm
  function maskEnvLines(text: string): string {
    return text.replace(ENV_LINE, (whole, lead, name, sep, value) => {
      const kind = classifyName(name)
      return kind && isMaskableValue(value, kind, false, undefined, name) ? `${lead}${name}${sep}${REDACTED}` : whole
    })
  }
  ```
  あわせて、上記の総当たり（28記号）を `packages/core/test/redactCases.ts` に加える。
- **見込まれる加点**：セキュリティ +1〜1.5
- **工数**：S
