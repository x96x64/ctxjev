## 用語

- **マスク**：秘密情報（パスワード、API キーなど）を `[REDACTED]` に置き換えること。
- **ブラインドコーパス**：マスクのコードを見ていない別のエージェントが、短い仕様だけから書いた行の集まり。「秘密を含む行」と「秘密に似ているが秘密ではない行」があります。半分（dev）は調整に使ってよく、もう半分（holdout）は最後に一度だけ測ります。
- **誤検出**：秘密ではない行を、マスクが書き換えてしまうこと。
- **境界ブルートフォース**：公開されている入口（関数・CLI・MCP のツール）に、壊れた値や極端な値を機械的に総当たりで入れるスクリプト。「生の TypeError」「NaN」「固まる」「壊れた出力」が出ないかを確かめます。
- **独立レビュー**：作業を見ていない別のエージェントに、PR の差分を調べてもらうこと。

### 改善10：公開の条件と配布の固定 — 一部修正

- コミット：`4631b99`、`0ac234a`
- 直したこと：`publish.yml` は、同じコミットで `main` への push の CI が成功していなければ公開しない（PR の CI は数えない）。今回の公開でも、この確認を通ってから公開された。
- 直していないこと：「タグは後から動かせる」問題。
  - 一度は marketplace.json にタグとあわせてコミットの `sha` も書いた。しかし独立レビューで、これが新しい問題を生むとわかった。Claude Code は `sha` を優先するので、リリースの PR をマージした時点で、まだ公開の検査（CI・ライブテスト・評価の関門）を通っていないコミットから、プラグインが入れられてしまう。
  - そのため `sha` の固定はやめて、0.6.1 と同じくタグだけにした。`sha` が知らないうちに戻らないように、`check-versions.mjs` は source/url/path/ref 以外の項目を拒む。
  - タグを動かせないようにするのは、GitHub の設定（タグの保護ルール）でできる。持ち主の操作が必要なので、[x96x64/ctxjev#22](https://github.com/x96x64/ctxjev/issues/22) に記録した。

## ブラインドコーパスの結果

- 作り方：マスクのコード（`redact.ts`）を見ていないサブエージェントが、短い仕様（`packages/core/test/blind-redact/README.md`）だけから行を書いた。乱数で dev と holdout に半分ずつ分けて、両方をコミットした（`cdbd207`）。
- 測り方は、何かを測る前に決めた（`packages/core/test/blindCorpus.ts`）。「検出」は、秘密のどの8文字の断片も出力に残っていないこと。「誤検出」は、秘密でない行が少しでも変わったこと。
- dev の半分（調整に使ってよい。[blind-dev.txt](2026-09-25-round-3-results/blind-dev.txt)）：

| 時点 | 秘密を含む行の検出 | 隠した秘密の数 | 誤検出（無害な行を変えた割合） |

| 0.6.1（`d55aa18`） | 69/91（75.8%） | 79/101（78.2%） | 3/43（7.0%） |

- dev で残った見逃し2件は、関数の引数に位置だけで渡される Algolia の管理キー（`algoliasearch('<app id>', '<key>')`、s067）と、CLI の動詞の後の裸の UUID（`snyk auth <uuid>`、s068）。どちらも名前や接頭辞の手がかりが無く、ほかの無害な値と区別できないため、足していません。

### holdout の半分（公開後に一度だけ測定）

- 0.7.0 のリリースのコミット（`b0dd13d`）で、公開の後に `scripts/redact-blind.ts holdout` を一度だけ実行した（[blind-holdout.txt](2026-09-25-round-3-results/blind-holdout.txt)）。
- holdout の行は、この測定の前にも後にも見ていない。調整にも使っていない。スクリプトは割合だけを出し、どの行を見逃したかは出さない。

| 0.7.0（`b0dd13d`） | 秘密を含む行の検出 | 秘密を丸ごと残さなかった行 | 隠した秘密の数 | 誤検出（無害な行を変えた割合） |
|---|---|---|---|---|
| dev（調整に使った半分） | 89/91（97.8%） | 89/91（97.8%） | 99/101（98.0%） | 0/43（0.0%） |
| **holdout（一度だけ）** | **84/91（92.3%）** | **85/91（93.4%）** | **98/106（92.5%）** | **6/42（14.3%）** |

- **dev の数値は楽観的だった。** holdout での検出は 92.3%（dev は 97.8%）。誤検出は 14.3%（dev は 0.0%）で、秘密ではない 42 行のうち 6 行を書き換えた。dev の誤検出 0% は、dev の見逃しと誤検出を見ながら規則を足した結果で、初めて見る行には当てはまらなかった。
- 0.6.1 の holdout での値は測っていない。holdout は一度だけ測る決まりなので、比べるために 0.6.1 でもう一度測ることはしなかった。そのため、holdout の上で 0.6.1 より良くなったかどうかは、この結果からは言えない。
- holdout は使い切った。これから `redact.ts` を変えても、この holdout で測った値はもう「見ていないデータでの値」ではない。次に独立に測るには、新しいブラインドコーパスが要る。
- 測る直前に、`scripts/redact-blind.ts` が 0.7.0 のコードを読み込めないことに気づいた。0.7.0 の `redact.ts` は `validate.ts` も使うのに、スクリプトはそのファイルをコピーしていなかった（PR #19 の `f242e42` 以降）。製品のコードではなく、測る道具の問題。この記録の PR で直し、直したスクリプトで測った。直した後も、dev の数値はそれまでに測った値と同じだった。

## 境界ブルートフォースの結果

`scripts/boundary-bruteforce.mjs`（CI で毎回実行）。対象は `pruneContext`、`summarizeSavings`、`pruneEntries`、`scoreEntries`、`estimateTokens`、`redactSecrets`、`pruneMessages`、`messagesToEntries`、CLI の `analyze`・`prune`、MCP の2つのツール。型違い・欠け・NaN・±Infinity・±1e308・巨大な文字列・Unicode の難しい文字などを入れる。どちらの行も、0.7.0 のスクリプトで測った（[boundary-bruteforce.txt](2026-09-25-round-3-results/boundary-bruteforce.txt)）。

| 対象 | 事例数 | 違反のあった事例 |
|---|---|---|
| 0.6.1（`d55aa18`） | 1,937 | 157（生の例外 111、NaN 33、時間切れ・強制終了 12、壊れた結果 5。1事例で複数の違反もある） |
| 0.7.0（`b0dd13d`） | 1,958 | 0 |

0.6.1 で見つかった主なもの：

- ゴールや `content` が文字列でないと、生の TypeError（`text.matchAll is not a function`、`out.replace is not a function`、`Cannot read properties of undefined`）。
- 時刻が無い・文字列・±Infinity だと、`scoreEntries` の `recency` が NaN。MCP では、時刻 ±1e308 で `recency: null`。
- CLI の `analyze`・`prune` で、`sourceTokens` がオブジェクトのとき、時刻が ±1e308 のとき、1e308 トークンの項目が2つあるときに、出力に NaN。
- 長い文字の並び（`█` × 100,000、`x` × 200,000、`a.a.a` × 200,000 など）で時間切れ（いちばん長いもので 234.0 秒、上限は 5 秒か 30 秒）。`!!` と結合文字 × 200,000 では、スタックがあふれて落ちた（`Maximum call stack size exceeded`）。
