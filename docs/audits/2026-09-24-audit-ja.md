## 4. カテゴリ別の詳細レビュー

用語メモ（初出のみ）：
- **モノレポ**＝複数のパッケージを1つのリポジトリで管理する形。**pnpm**＝そのためのパッケージ管理ツール。
- **npm**＝JavaScript 部品の公開・配布サイト。**フック**＝Claude Code が特定の瞬間（圧縮の直前など）に自動実行する小さなプログラム。
- **圧縮（コンパクション）**＝会話が長くなりすぎたとき、Claude Code が過去の会話を要約に置き換えて短くする処理。
- **トークン**＝AI が文章を数える単位（おおよそ単語の断片）。**プロンプトキャッシュ**＝前回と同じ会話の先頭部分を安く再利用する仕組み。途中を変えると、そこから先は再計算になる。
- **MCP**＝AI ツールが外部の道具を呼び出すための共通規格。**CI**＝変更のたびにビルドやテストを自動で走らせる仕組み。
- **ホールドアウト**＝設計や調整に一切使わず、最後の判定のためだけに取っておくデータ。**事前登録**＝結果を見る前に「何をどう測り、どう判断するか」を文書で固定しておくこと。
- **ブートストラップ信頼区間**＝手元のデータを何千回も復元抽出し直して「結果がどの程度ぶれうるか」の幅を求める統計手法。
- **ベースライン**＝比較の基準となる単純な方法。ここでは「新しい方を残す＝単純な切り捨て（recency）」「キーワード一致（local）」「ランダム順」。

### 4.1 中核機能と正しさ（11.0 / 15）

**良い点**
- `pruneMessages()`（Anthropic 形式の会話を剪定する関数）の不変条件は非常に堅い。独自に作った厳格な検証器（API が連続する同じ話者のメッセージを結合する挙動まで再現し、ツール呼び出しと結果の直後対応、tool_result が先頭に来る規則、先頭メッセージと末尾 N 件の不変、元に無いブロックの混入を検査）で、サンプル1件＋評価セッション21件 × 採点方式2種 × オプション7通り＝**308回の実行で違反0件**。検証器自体も、わざと壊した入力3種をすべて検出することを確認済み。
- `packages/core/src/anthropicMessages.test.ts:269-326` にランダム化された150回の性質テスト（property test＝ランダムな入力で常に成り立つべき性質を確かめるテスト）があり、設計段階から不変条件を意識している。
- CLI・MCP・プラグインの主要機能は、キー無し（オフライン）の経路で README どおり動作した（例外は下記の3・4）。プラグインのマニフェストは `claude plugin validate`（Claude Code 2.1.282）で合格。

**問題点と根拠**
1. **「削ったのに会話が増える」バグ**（`packages/core/src/anthropicMessages.ts:199`, `:278`）。削除箇所に入れる注記文（marker, 約36トークン）の分を差し引く前に `minSavedTokens` を判定しているため、小さな項目（6トークン）を1つ消すと注記の方が大きく、結果が `savedTokens: -30` になる。既定の設定（recency 採点・marker 有効）でも再現し、しかもプロンプトキャッシュを無駄に無効化する。
2. **超大規模入力でのクラッシュ**（`anthropicMessages.ts:257` の `Math.min(...changedAt)`）。ツール呼び出し15万件の会話で `RangeError: Maximum call stack size exceeded`。同じ危険をコード内の別箇所（`recency.ts`, `packages/cli/src/report.ts`）では明示的に回避しているのに、ここだけ残っている。
3. **公開版で README の Quick Start が動かない**。npm の最新は `0.5.0`（`npm view ctxjev-cli version`）で、そこでは既定が Jev のため `ctxjev analyze …` はキー無しで `✖ TYPESAFE_API_KEY is not set` となり、`--scorer` も存在しない（`Unknown option '--scorer'`）。README（`README.md:314`）は未リリースの 0.6.0 の挙動を「現状」として説明している。
4. `packages/cli/README.md:77` は「`--help`/`--version` はコマンドの前後どちらでも動く」とするが、`ctxjev analyze --version` は `Unknown option '--version'` で終了コード1。
5. **Claude Code 記録の重複IDで全体停止**。同じ `uuid` のレコードが2つあるだけで `duplicate entry id "u1"` となり解析全体が失敗（`packages/core/src/prune.ts:114`、ID は `claudeCodeTranscript.ts:120` でそのまま採用）。プラグインでは「何も保存しない」結果になる。実際の記録で重複が起きうるかは未確認。
6. 壊れた（途中で切れた）JSON に対して「Claude Code の .jsonl としても解釈できない」という紛らわしいエラーを出す（`packages/cli/src/transcript.ts:24`）。
7. 長い絵文字列を切り詰めると、奇数位置で切れた場合にサロゲートペア（絵文字を表す2つ組の文字コード）の片割れが残る（`packages/core/src/entryText.ts` の `truncate`）。

**減点理由**：1a −2（Jev 経路未検証＋公開版と説明の不一致＋記載誤り）、1b −1（負の節約量・スタック溢れ）、1c −1（重複IDでの全停止ほか）。

### 4.2 有効性（3.5 / 10）

**良い点**
- 作者は「効果が無かった」結果を README の冒頭（`README.md:48-56`）に明記し、既定の採点方式を Jev から単純な切り捨て（recency）へ変更した。結果に従って製品の既定を変えたことは誠実で、珍しい。
- 採点方式に依存しない部分（ユーザーの発言を常に残す `keepUserText`、削除箇所の注記 `marker`、ツール呼び出しの対を壊さない削除、キャッシュへの影響報告）は、エージェントを自作する人にとって実用的な安全装置である。

**問題点と根拠**（すべてリポジトリ自身の保存データから再計算）
1. **主指標（課題の成功率）では差が無い**：ホールドアウト6課題×3回で、Jev もrecency もすべて100%、差は **+0 [+0, +0]**（Haiku 4.5・Sonnet 5 とも。`node eval/tasks.mjs --report eval/results/tasks-holdout*.json` で再現）。
2. **副指標（必要な事実がどれだけ残るか、25%予算）では、Jev はキーワード一致にもランダム順にも負けている**。オフラインで再計算できる基準値（`node eval/run.mjs --split holdout`、キー無し）は、キーワード一致 **28.3%**、ランダム順 **26.5%**、ラベル順（理想に近い順位付け）**32.7%**、recency **0.0%**。README が示す Jev は 15.6%（事前登録文書では 18.5% または 20.7%）で、**ランダムに並べるより悪い**。README（`README.md:191-204`）はキーワード一致との比較には触れているが、ランダム順より劣る点は書いていない。
3. 開発用データ（dev、設計に使ったので楽観的）でも、Haiku では +10 [0, +30]（20回中2回、1課題のみ）、Sonnet 5 では −5 [−15, 0]。質問応答評価では Jev − 切り捨て = +8 [−1, +18] で0を含む。プラグインの効果は +5 [0, +15]（dev のみ）で、ホールドアウトでは評価自体が失敗して未実施。
4. **既定（recency）の実用上の注意**：既定では `goal`（目標文）が完全に無視される（`packages/core/src/prune.ts:127`）。既定の閾値（`types.ts:45` の dropBelow 0.3）と組み合わさり、内容に関係なく「古い方から約30%を削除、次の30%を要約候補」になる（例：pagination-bug で60件中18件削除）。ctxjev 形式では最初のユーザー依頼（j1, s1, p1 など正解ラベルで「重要」）も削除される。
5. **オフライン採点（`--scorer local` / `--offline`）は既定閾値では実用にならない**。正解ラベル付きサンプルで、重要項目の削除数は pagination-bug **13/14**、session-logout **8/9**、invoice-date-ja **8/11**（`pruneContext(..., {scorer:'local'})` で計測）。キーワード一致の点数は0.3に届きにくく、閾値が Jev の確率向けにしか調整されていない。
6. プラグインのオフライン代替は、合成サンプルで最重要の結論（"Found it — … never calls removeListener()"）を残さず、関連度0.13の1件だけを残した（キーワードが目標文と重ならないため）。

**減点理由**：2a −4.5（ホールドアウトで優位性なし、副指標で基準以下）、2b −2（既定は切り捨てに過ぎず、オフライン代替は閾値不整合、npm 版は依然 Jev 必須）。

**問題点と根拠**
1. **主指標は原理的に差が出にくい設計**：ホールドアウトの制約はすべてユーザー発言にあり、`keepUserText` がどの採点方式でも残す。実際に full（全履歴）も両剪定も100%、goal-only（目標だけ）が0%という天井効果。事前登録文書自身が「差が出ないかもしれない」と認めている（`PREREGISTRATION.md:51-53`）。また Jev の順位付けは課題ごとに1回しか計算されず（`eval/tasks.mjs:168`）、「3回の反復」はエージェント側の揺らぎしか測っていない。
2. **副指標の比較相手（recency）が構造的に0%**：副指標は実装フェーズを含む**全会話**で測る（`eval/run.mjs:139`）。ホールドアウト6セッションでは、切り取り点（「では修正して」）以降が全トークンの22〜43%を占め、事前に付けた「必要な事実」のラベルは**切り取り点以降を1つも指していない**（0/7〜0/8）。一方 dev の記録セッション10件では、どれも1つずつ切り取り点以降の事実（「修正後のテスト結果」）がラベル付けされている。つまり recency の0%はラベル付けの違いによる人工的な結果で、ROADMAP（`ROADMAP.md:12-14`）が「推測」とする dev/ホールドアウトの逆転の説明にもなる。

## 6. 重大な問題トップ5

1. **中核価値（Jev による選別）の有効性が実証されていない上、副指標の分析が歪んでいる**：主指標は差 +0、副指標では Jev（15.6〜20.7%）がキーワード一致（28.3%）にもランダム順（26.5%）にも劣る。比較相手の recency が0%なのはラベル付けと測定範囲による構造的な結果。README の数値は事前登録文書の2つの結果のどちらとも合わず、元データも保存されていない（`README.md:191-197`、`PREREGISTRATION.md:149-152`、`eval/run.mjs:139`）。
2. **秘密情報マスキングの網羅不足と部分漏洩**：40形式中21形式が素通り（JSON 形式の認証情報、URL 内パスワード、主要サービスのトークン等）、切り詰め後マスクでトークンの一部が送信内容に残る（`redact.ts:24`、`entryText.ts:60`）。プラグインはキーがあれば実際の会話を毎回外部送信する。
