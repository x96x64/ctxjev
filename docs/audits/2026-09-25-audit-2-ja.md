## 4. カテゴリ別の詳細レビュー

用語の補足：以下で出てくる主な用語を最初に説明します。

- **モノレポ**：複数のパッケージを1つの保管場所でまとめて管理する方式。
- **フック**：Claude Code が決まったタイミングで自動実行する小さなプログラム。
- **剪定（プルーニング）**：会話の履歴から不要な部分を削ること。
- **Jev**：TypeSafe AI 社のAIモデル。文章は書かず、「はい／いいえの確率」などの判定だけを高速に返す。
- **ベースライン**：比較の基準にする単純な方法。
  - **単純切り詰め（`recency`）**：新しいものから残し、古いものから捨てる。
  - **キーワード一致（`local`）**：目標の文と同じ言葉を含む度合いで判定する。
- **トークン**：AIが文章を数える単位。おおよそ単語や文字のかたまり。

### 4.1 中核機能と正しさ（11 / 15）

**良い点**
- **4つのパッケージはすべて実際に動きました。**
  - `ctxjev-cli`：`analyze`と`prune`を、サンプル8ファイル×採点方式2種で実行しました。Claude Code 形式への`prune`は仕様どおり拒否され、それ以外は正常終了しました。
  - `ctxjev-mcp`：MCP（AIツールに外部機能を「道具」として提供する共通規格）のサーバーです。標準入出力で起動すると、`score_relevance`と`prune_history`の2つのツールを公開しました。不正な入力、重複したID、しきい値の逆転は、どれも`isError`付きの丁寧なエラーで返しました。
  - プラグインのフック：キーが無い状態で動かすと、オフライン採点に切り替わり、状態を`~/.claude/ctxjev/`に保存しました。
- **`pruneMessages()`の不変条件は堅牢です。**
  - 不変条件とは、「どんな入力でも必ず守られるべき約束」のことです。
  - 守るべきは、tool_use（AIが道具を呼んだ記録）とtool_result（その結果の記録）の対を壊さないことです。
  - 私は独自の厳密な検査スクリプトを書きました。「結果は必ず直前のアシスタント発言への応答であること」「結果ブロックが先頭に来ること」「空のメッセージがないこと」を確かめます。
  - サンプル2件×2方式で違反は0でした。
  - リポジトリ自身にも、150通りのランダムな会話で検査する性質テストがあります（`packages/core/src/anthropicMessages.test.ts:269-326`）。
- **エッジケースへの耐性が高いです。**
  - 空のファイル、エントリ0件、メッセージ0件、1件だけ、壊れたJSONのどれでも、分かりやすいメッセージを出すか正常に終了しました。
  - 6.4MBのツール出力も3.1秒で処理しました。
  - CLIは「キーが無い」「ファイルが無い」「しきい値が範囲外」を1回の実行でまとめて報告します（`packages/cli/src/index.ts:124-160`）。

**問題点と根拠**
1. **READMEの出力例が再現できません。**
   - README.md:131-147 とパッケージのREADME（`packages/cli/README.md:37-57`）は、Jevで採点した出力を「リポジトリのサンプルに対する実際の出力」として載せています。
   - しかし既定の採点が`recency`に変わったため、同じコマンドを実行すると「Scored by position alone」という別の結果が出ます。
2. **`--version`の記述が誤りです。**
   - `packages/cli/README.md:77`には「コマンドの前でも後でも動く」とあります。
   - 実際に`ctxjev analyze --version`を実行すると`✖ Unknown option '--version'`（exit 1）になりました。
3. **`--scorer local`（オフライン採点）を既定しきい値のまま使うと、破壊的な結果になります。**
   - 既定しきい値は Jev の確率スケールに合わせて作られています（dropBelow 0.3）。
   - 一方、キーワード一致の点数はほとんどが0.1前後です。
   - その結果、`prune --scorer local`は次のように削りすぎました。

   | サンプル | 削除したエントリ | 失われた「関連あり」（正解ラベル） |
   | --- | --- | --- |
   | pagination-bug.json | 60件中59件 | 14件中13件 |
   | session-logout.json | 28件中26件 | 9件中8件 |
   | invoice-date-ja.json | 28件中20件 | 11件中8件 |

   - プラグイン側のコードは、この尺度の違いを認識しています（`packages/claude-plugin/src/select.ts:18-20`）。しかしCLIとcoreでは対処されていません。
4. **節約量がマイナスでも変更が適用されます。**
   - 既定の`pruneMessages()`を`anthropic-messages.json`に適用すると、`savedTokens: -10` と表示され、プロンプトキャッシュ146トークン分が無効になりました。
     - プロンプトキャッシュとは、AIに毎回送る共通の前半部分を保存し、安く速く再利用する仕組みです。
   - 原因：「節約が`minSavedTokens`未満なら何もしない」判定（`packages/core/src/anthropicMessages.ts:199`）が、削除注記の追加コストを差し引く前に行われています（差し引きは:278）。
5. **「最新ターンは触らない」という主張は不正確です。**
   - README.md:124-125 は「先頭メッセージと最新ターンは触らない」と書いています。
   - 実際に守られるのは「最後の`protectLast`件（既定2件）のメッセージ」だけです（`anthropicMessages.ts:164-166`）。
   - 最新のユーザー指示の後にツール呼び出しが3往復続く会話を作って試すと、`tool:m1`と`tool:m2`（最新ターン内の呼び出し）が削除されました。
6. **1行の重複で解析全体が失敗します。**
   - 1行だけ重複した Claude Code の記録を与えると、`✖ duplicate entry id "u1"`で解析全体が失敗しました（`packages/core/src/prune.ts:111-117`）。
   - プラグインでも保存が0件になります。
   - 実際の記録に重複が起こるかは未検証ですが、1行の不整合で機能全体が止まる設計です。
7. **一部のオプションが黙って無視されます。**
   - ctxjev独自形式への`prune`では、先頭・末尾の保護がありません。
   - それにもかかわらず`--protect-last 5`を付けてもエラーにならず、黙って無視されます（`packages/cli/src/index.ts:226-233`）。

**減点理由**
- 説明どおりに動かない箇所（出力例、`--version`、`local`の既定しきい値）で−2。
- マイナス節約と「最新ターン」の誇張で−1。
- 重複記録での全体失敗と黙って無視されるオプションで−1。

### 4.2 有効性（3.5 / 10）

**良い点**
- 保存された結果を再計算しました（数値は5章）。25%の予算まで削っても、ユーザー発言の保持と削除注記を組み合わせれば、ホールドアウトのタスクは全件成功しました。
  - **ホールドアウト**とは、設計の調整に使わず最後の検証のためだけに取っておくデータのことです。
  - 「履歴を4分の3削っても小さなタスクなら困らない」ことは、弱いながらも示されています。
  - 同じ条件で、目標文だけを渡すと0%でした。
- 開発用データでは、ユーザー発言の保持と削除注記を付けると、Jev採点の成功率が90%から100%に上がりました。

**問題点と根拠**
1. **主要評価（タスク成功率）は、原理的に差が出ない設計でした。**
   - 各タスクで採点に効く制約は、すべてユーザーの発言（`task.json`の`prompts`）の中にあります。例：`examples/eval-tasks/coupon-stacking/task.json`。
   - 比較した2条件（`jev+user+marker`と`recency+user+marker`）は、どちらもユーザー発言を必ず保持します（`anthropicMessages.ts:166`）。
   - つまり両条件とも、合否を決める情報を必ず持っています。結果が18/18対18/18になるのは当然で、「同等」の証拠にはなりません。
   - 事前登録文書自身も、この点を副次評価を加えた理由として認めています（`packages/core/eval/PREREGISTRATION.md:51-53`）。
2. **ホールドアウトの保持率では、Jevはランダム選択に負けています。READMEはこれを載せていません。**
   - 私が`eval/run.mjs --split holdout`をオフライン（キー無し）で再実行した結果、予算25%での保持率は次のとおりでした。

   | 選び方 | 保持率 |
   | --- | --- |
   | キーワード一致 | 28.3% |
   | 単純切り詰め | 0.0% |
   | ランダム | 26.5% |
   | 正解ラベル順 | 32.7% |
   | Jev（README） | 15.6% |
   | Jev（事前登録文書の2回の実行） | 18.5% / 20.7% |

   - Jevはランダムより低い値です。
   - README.md:191-204 は「Jevは切り詰めより+15.6ポイント多く残す」と書いています。しかし、その切り詰めの0%自体が、次の項目で述べる評価の歪みから生じた値です。
3. **その「単純切り詰め0%」は、ラベル付け手順の違いによる見かけの結果です。**
   - ホールドアウト6件：修正指示より後の50エントリに、「関連あり」ラベルが1つもありません。
   - 開発用10件：修正指示より後の97エントリのうち、63件が「関連あり」です（本人がスクリプトで確認）。
   - `run.mjs`は、修正指示の後ろまで含むセッション全体を採点します（`packages/core/eval/run.mjs:99,139`）。一方、`tasks.mjs`は修正指示の位置で履歴を切っています（`tasks.mjs:167`）。
   - 修正指示の位置で切って再計算すると、ホールドアウトの切り詰めの保持率は0%から25〜50%に上がりました。
   - ROADMAP.md:12-14 は「キーワードがJevに勝った理由は未確認」としています。しかし、このラベル手順の差が最も有力な説明です。
4. **開発用データでの優位も弱いものです。**
   - Haikuで+10ポイント（95%区間 [0, +30]）ですが、これは1タスク（`webhook-dedupe`）だけで生じた差です。
   - Sonnet 5では−5ポイントでした。
   - 回答正答率の評価では+8.3ポイントでしたが、区間が0をまたいでいます（[−0.9, +18.3]）。
   - プラグインの効果は+5ポイント [0, +15] で、0.4.0方式の目標設定では−5ポイントでした。
5. **既定の`recency`は、誰でも数行で書ける単純な切り詰めです。**
   - `analyze`の「score」は、位置だけで決まる数値になりました。
   - それでもCLIの凡例は「高いほど目標に関連」と表示します（`packages/cli/src/report.ts:33`）。

**減点理由**
- 設計に使っていないデータで、単純な方法（ランダム・キーワード・切り詰め）を上回った証拠がありません（−4.5）。
- 既定の採点方式ではツールの独自価値が小さくなっています（−2）。

### 4.3 評価の厳密さと主張の誠実さ（5 / 10）

**良い点**
- 事前登録を実行し、計画の本文は結果を見た後も書き換えていません。後から加えた変更は「Changes after registration」に明記しています。
  - **事前登録**とは、結果を見る前に「何を、どう比べ、どう判断するか」を文書で固定しておくことです。
