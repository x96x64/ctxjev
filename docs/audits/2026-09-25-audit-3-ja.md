## 4. カテゴリ別の詳細レビュー

### 4.1 中核機能と正しさ（12.00 / 15）

**このツールの構成（用語の説明をかねて）**

- **モノレポ**：1つのリポジトリに複数のパッケージ（配布の単位）をまとめる作り方です。ここでは次の4つが入っています。
  - `ctxjev-core`：中核の処理
  - `ctxjev-cli`：コマンドラインで使う道具
  - `ctxjev-mcp`：AI アプリから呼べる「MCP サーバー」
  - `ctxjev-claude`：Claude Code のプラグイン
- **採点方式**：どの部分を残すかを決める方法は4つです。
  - `recency`（既定）：新しさだけで決める
  - `local`：目標とのキーワードの重なりで決める
  - `jev`：Jev に判定させる（自分で選んだときだけ使う）
  - 自作の関数
- **判定の流れ**：各項目の点数を閾値で「残す／要約候補／削る」に分けます。
  - 0.3 未満は削る
  - 0.6 未満は要約候補
  - それ以上は残す

**良い点**

- **README の例と出力が一致する。** npm から入れた公開版 `ctxjev-cli@0.6.1` で `ctxjev analyze examples/sample-transcripts/checkout-bug.json` を実行しました。出力は `README.md:143-155` と一字一句同じでした。
- **公開物がソースから再現できる。**
  - npm の公開物（配布用の圧縮ファイル、tarball）は、コミット `d55aa18` から `pnpm pack` で作ったものとバイト単位で一致しました。
  - npm の「来歴証明」（どのソースと CI から作られたかを示す署名）も付いています。
- **会話の構造を壊さない。**
  - 評価用の会話 21 件それぞれに6通りの設定で `prune` をかけ、計 126 回を独自の検査スクリプトで確かめました。違反は0件です。
  - 確かめた約束：ツールの呼び出しと結果の対、結果が呼び出しの直後にあること、最初のメッセージ、最新のターン、最後の2メッセージ。
- **判定が食い違わない。** `analyze`（判定を表示するだけ）と `prune`（実際に削る）の判定は、88 組すべてで一致しました。
- **予算指定が効く。** `--target-tokens 2000` で結果は 1,786 トークンになり、目標内に収まりました。トークンは、AI が文章を数える単位です。
- **前回の監査で指摘された正しさの問題の多くが直っている。**
  - 削っても会話が増える「マイナスの節約」
  - 15万件でのクラッシュ
  - 重複 ID で解析全体が止まる問題
  - 未知の採点方式が黙って recency 扱いになる問題（`packages/core/src/prune.ts:122-124` で拒否するようになった）
  - 最新ターンの保護（`protectLastTurn`）

**問題点と根拠**

1. **予算超過フラグが注記の分を数えない。**
   - 予算内に収める処理（`packages/core/src/anthropicMessages.ts:249-257`）は、あとで加える注記（`:326-334`）のトークンを勘定に入れていません。
   - そのため `overBudget: targetTokens !== undefined && remaining > targetTokens`（`:354`）は、結果が目標を超えていても `false` になることがあります。
   - 目標値を 807 通り変えて調べたところ、38 通りでこの誤りが起きました。
2. **独自形式の `prune` が、最初の依頼と未知の項目を消す。**
   - `ctxjev prune` を ctxjev 独自の形式にかけると、「削る」と判定された項目はすべて削除されます（`packages/cli/src/index.ts:298-303`）。
   - 既定の recency では最初の依頼も「古い」ので削られます。例：`checkout-bug.json` では「removed 2 of 7 entries … scored by position alone」と表示され、最初の依頼 `e1` が消えました。日本語のサンプルでも、ユーザーの目標の項目が消えました。
   - 出力は `{goal, entries}` だけなので、`groundTruth` のような元ファイルの他の項目も黙って落ちます。
3. **とても長い文字列で処理が固まる。**
   - トークンを数える `estimateTokens()`（`packages/core/src/tokenEstimate.ts:7-9`）は、`encode(text).length` を上限なしで呼んでいます。
   - 同じ文字が続くと、かかる時間が長さの二乗に比例して増えました。

     | 入力 | かかった時間 |
     | --- | ---: |
     | `x` × 10万 | 8.7 秒 |
     | `x` × 20万 | 36.7 秒 |
     | 空白 × 10万 | 9.8 秒 |
     | `█` × 10万 | 82.5 秒 |

   - 500万文字の項目に `ctxjev analyze` をかけると、120 秒で強制終了しても終わりませんでした。
   - base64・16進・普通のログは速く、問題になるのは特殊な入力だけです。ただし、ログの罫線や区切り線のように実際に起こりうる入力でもあります。
4. **入力の検証に漏れがある。**
   - `"sourceTokens":"100"`（数値ではなく文字列）を渡すと、`~0100 / 0100-501 tokens (NaN%)` と表示されました。`packages/cli/src/transcript.ts:120-143` の `validateEntry` が `sourceTokens` を検証していないためです。
   - `text` の無い text ブロックを渡すと、`Cannot read properties of undefined (reading 'replace')` という生のエラーで終わりました。
   - 時刻が ±1e308 のように極端だと、`packages/core/src/recency.ts` の計算が Infinity から NaN になります。CLI は `decideAction received a NaN score` で止まり、MCP の `score_relevance` は `recency: null` を返しました。
5. **古い説明が残っている。**
   - CLI のヘルプ（`packages/cli/src/index.ts:30`）は「score and prune AI agent context with Jev」と書いています。既定は Jev ではありません。
   - README の Quick Start（`README.md:408`）は `transcript.jsonl` という、同梱されていないファイルを使っていて、そのまま実行すると失敗します。

- 1a（−1.0）：問題点5と CLI の README・プラグインの説明文の古い記述（4.7 節）。プラグインの実機インストールを確認できていない分も含めました。

### 4.2 有効性（3.00 / 10）

**用語**

- **dev**：設計や調整に使ってよい評価データ。
- **ホールドアウト**：最後の判定用に取っておき、調整には使わない評価データ。
- **事前登録**：結果を見る前に、判定のルールを記録して固定しておくこと。

**良い点**

- **dev では前向きな結果がある。**

### P0（すぐに直すべきもの）

#### 改善1：マスクの「飲み込み」を直し、URL の中のトークンと不足している形式を加える

- **優先度**：P0
- **問題**：名前が資格情報でない「名前: 値」が、値の中の本物の `NAME=秘密` を隠してしまいます。URL の問い合わせ部分（`?token=`）も隠れず、よくあるトークンの形式も一覧にありません。
- **根拠**：`packages/core/src/redact.ts:90`、`:158-166`、`:22-42`。検証 20〜23（76 例中 52、`out: ` 付きで 36）。
- **改善案**
  - 資格情報でない名前に一致した場合は、値の部分に同じマスクをもう一度かけます。値は元の一致より必ず短いので、繰り返しは必ず終わります。
  - URL の問い合わせのうち、資格情報らしい名前のものを隠します。
  - 一覧に形式を加えます。
  - 今回の 76 例を、`packages/core/test/redactCases.ts` の表に回帰テスト（直した不具合が戻ったら失敗するテスト）として追加します。

  ```ts
  // redact.ts（158行目付近）の案
  out = out.replace(ASSIGNMENT, (match, quote, name, sep, escaped, dq, sq, bq, bare, offset, whole) => {
    const kind = credentialKind(name)
    const value = escaped ?? dq ?? sq ?? bq ?? bare ?? ''
    if (!kind || !isMaskableValue(value, kind, bare !== undefined, whole[offset + match.length])) {
      // 「Error: DB_PASSWORD=…」「https://…?token=…」：外側の名前は資格情報でなくても、
      // 値の中に別の代入や URL の問い合わせがあり得るので、値だけをもう一度調べる
      return bare !== undefined && /[=:?&]/.test(bare)
        ? `${quote}${name}${quote}${sep}${redactSecrets(bare)}`
        : match
    }
    /* …既存の処理… */
  })

  const QUERY_SECRET = /([?&#](?:access_token|refresh_token|id_token|token|api_?key|key|secret|password|passwd|sig|signature|auth)=)([^&#\s"'<>]+)/gi
  out = out.replace(QUERY_SECRET, (_m, head: string) => `${head}${REDACTED}`)

  // TOKEN_PATTERNS に追加する例
  [/\bhvs\.[A-Za-z0-9_-]{24,}\b/g, 'vault'],
  [/\bdop_v1_[a-f0-9]{64}\b/g, 'digitalocean'],
  [/\blin_api_[A-Za-z0-9]{40}\b/g, 'linear'],
  [/\bshp(?:at|ss|ca|pa)_[a-fA-F0-9]{32}\b/g, 'shopify'],
  [/\bpypi-[A-Za-z0-9_-]{50,}\b/g, 'pypi'],
  ```

#### 改善2：トークン数えに上限を設け、二乗的な遅延を無くす

- **優先度**：P0
- **問題**：同じ文字が長く続く文字列で、`encode()` の時間が二乗的に増えます。
- **根拠**：`packages/core/src/tokenEstimate.ts:7-9`。検証 17・18。
- **改善案**
  - 同じ文字の長い連続は、固定の長さで数えてから掛け算します。
  - 残りは一定の長さで区切って数えます。区切りの長さは計測して決めます。
  - 見積もりなので、区切りによる数トークンのずれは許容できます。
  - 「10万文字の `█` が1秒以内」のような時間制限つきのテストを加えます。

  ```ts
  const RUN = /(.)\1{63,}/gsu            // 同じ文字が 64 個以上続く部分
  const PIECE = 4096                     // 区切りの長さ（計測して調整）
  export function estimateTokens(text: string): number {
    let tokens = 0
    const rest = text.replace(RUN, (run: string, ch: string) => {
      tokens += Math.ceil([...run].length / 64) * encode(ch.repeat(64)).length
      return ' '
    })
    for (let i = 0; i < rest.length; i += PIECE) tokens += encode(rest.slice(i, i + PIECE)).length
    return tokens
  }
  ```

- **見込まれる加点**：+0.75（1c +0.5、4c +0.25）
- **工数**：S
